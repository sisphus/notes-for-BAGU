| 用“连接身份空间 ≠ 实际服务能力”理解 C10K | 从 TCP 四元组理论连接数推断服务器容量，或判断调大 fd 上限是否已经解决高并发问题时 | 服务端固定 IP/端口；客户端 IP/端口组合；理论 `2^48`；文件描述符预算；每连接内核内存；进程/线程执行模型；CPU 与网络工作量 | 能先用四元组说明连接怎样被区分，再用 fd、内存、执行实体和工作量说明实际容量由最小预算决定，不把可编号数量当可服务数量 | 把 `2^48` 当单机可承载量；认为调大 `ulimit` 就解决 C10K；只列 fd/内存却忽略一连接一进程/线程的调度与切换成本 | Stable |
| 用“连接数 ≠ 执行实体数”理解 I/O 多路复用 | 大量 Socket 已建立但只有少量连接当前活跃，需要判断是否必须为每条连接维护一个等待中的进程或线程时 | Socket 连接对象；进程/线程执行实体；阻塞等待；就绪事件；一个等待接口关注多个 fd；时间复用；短小非阻塞事件处理 | 能说明多路复用仍维护全部连接对象，但把连接数与等待执行实体数解耦，让一个或少量事件循环只处理本轮就绪子集 | 认为多路复用减少了 Socket 数量；认为一个进程在单核上同时并行执行多个处理函数；在事件循环中执行长期阻塞操作却认为不会影响其他连接 | Stable |
| 用“全量集合复制 + 内核/用户双扫描”运行 select/poll | 关注大量 fd 但每轮只有少量就绪，需要解释 select/poll 的成本为何仍随关注集合扩大时 | 用户关注集合；用户到内核全量复制；内核线性扫描；结果集合复制回用户；用户线性扫描；select 位图与 `FD_SETSIZE`；poll 动态线性数组；`N` 与就绪数 `k` | 能运行一次 `用户集合 -> 内核扫描 -> 结果返回 -> 用户扫描`，数出两次集合复制和两次线性扫描，并说明 poll 只去掉固定容量表示限制而未消除 `O(N)` 本质 | 只记 select 的 1024 上限；认为 poll 动态数组会只返回 `k` 个就绪项；漏掉用户态再次扫描；把线性 `O(N)` 说成严格指数复杂度 | Stable |
| 用“持久关注集合 + 就绪列表”运行 epoll | 已关注大量 fd 但每轮只有少量事件，需要解释 epoll 怎样避免反复提交和扫描整个关注集合时 | `epoll_ctl`；内核红黑树；持久关注关系；Socket 事件回调；就绪链表；`epoll_wait`；就绪事件数组；`N` 与 `k`；`__put_user`；非共享内存 | 能把红黑树定位为长期保存 `N` 个关注项，把就绪链表定位为本轮 `k` 个事件，并说明 `epoll_wait` 只复制就绪事件记录而不是共享或复制整个关注集合 | 把红黑树说成就绪队列；认为每次 `epoll_wait` 仍传入全部 fd；认为用户直接共享内核就绪链表、完全没有复制；把 epoll 所有操作都说成无条件 `O(1)` | Stable |
| 用“条件持续 vs 状态边沿”区分 LT 与 ET | Socket 已被报告可读但 handler 可能只处理部分数据，需要判断后续是否还会通知以及读取循环何时停止时 | LT 按可读条件持续通知；ET 按不就绪到就绪的状态边沿通知；非阻塞 I/O；循环读写；`EAGAIN/EWOULDBLOCK`；新数据形成新边沿 | 能预测只读部分数据后 LT/ET 的后续通知，并为 ET 写出“非阻塞循环处理到 EAGAIN”的正确策略 | 把 ET 说成 fd 一生只通知一次；认为 ET 只读一点也必然再次通知；阻塞 fd 上无限循环读取；把 EAGAIN 当成连接故障 | Stable |
| 用“就绪发现机制 ≠ 事件协调模式”区分多路复用与 Reactor | 看到 select/poll/epoll、事件循环、dispatch 或 Reactor，需要判断底层机制与上层模式分别解决什么问题时 | I/O 多路复用发现就绪 fd；Reactor 监听并按连接/读写事件分发；Acceptor、Handler；实际 `accept/read/send` 仍由应用执行 | 能把一次事件拆成“内核返回就绪 -> Reactor 按类型 dispatch -> 对应对象执行实际操作”，并反驳“Reactor 就是 epoll” | 把 epoll 与 Reactor 当同义词；认为多路复用已完成 read；只说事件驱动却无法指出事件到处理对象的映射 | Stable |
| 用“监听 fd -> Acceptor、连接 fd -> Handler”路由 Reactor 事件 | I/O 多路复用同时返回监听 fd 和已连接 fd 的事件，需要决定 dispatch 目标和下一步系统调用时 | Reactor 监听与分发；连接建立事件；Acceptor 与 `accept`；已连接 fd 读写事件；连接专属 Handler 与 `read/send` | 能根据就绪 fd 的角色把连接事件交给 Acceptor、普通读写事件交给对应 Handler，并说明两者分别执行的实际操作 | 让 Acceptor 读取普通客户端数据；让 Handler 在监听 fd 上处理新连接；把 dispatch 当成内核系统调用；认为创建 Handler 必然创建线程 | Stable |
| 用“一个事件循环的串行临界路径”判断单 Reactor 单执行实体 | 单 Reactor 单进程/线程中某个 Handler 业务耗时较长，需要预测其他已就绪连接是否会被延迟时 | 一个 Reactor；一个执行实体；串行 dispatch；Handler 的 `read -> 业务 -> send` 完整路径；多核利用；慢 Handler 的延迟传播 | 能从“唯一执行流正停在哪一步”判断其他事件何时才能被 dispatch，并说明 I/O 多路复用发现就绪不等于业务并行 | 认为 epoll 已返回多个就绪事件就会同时执行多个 Handler；认为慢 Handler 只影响自己的连接；忽略单执行实体无法并行业务和充分利用多核 | Stable |

| 用“就绪事件 vs 完成事件”区分 Reactor 与 Proactor | 网络库产生回调或通知，需要判断应用是否还要主动读写，以及数据是否已进入用户缓冲区时 | I/O 数据准备与数据交付两阶段；Reactor 的可读写就绪通知；Handler 主动 `read/write`；Proactor 的异步操作提交；系统完成 I/O；完成通知；用户缓冲区 | 能从通知时点和实际 I/O 执行者判断模式：就绪后应用读写是 Reactor，系统完成读写后回调是 Proactor | 把 epoll 可读通知说成数据已进入用户缓冲区；把非阻塞等同异步；把 Proactor 说成只是在 Handler 后增加线程池；说不出谁完成内核到用户的交付 | Stable |
