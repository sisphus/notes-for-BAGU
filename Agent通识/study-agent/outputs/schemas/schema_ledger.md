# Schema Ledger

Track reusable schemas, not every topic or detail.

| Schema name | Trigger situation | Compressed concepts | What the learner can do after acquiring it | Common failure signal | Status |
| --- | --- | --- | --- | --- | --- |
| decompose an Agent into decision, observation, and action | Need to explain what makes an AI system an Agent or diagnose why it fails | LLM as decision core, context as observation, tools as action, feedback loop | Identify which capability is present or missing and predict the resulting failure | Says "Agent = LLM + tools" but omits context, observation, or result feedback | Stable |
| run the four-step tool-calling loop | Need to trace how an LLM request becomes a real external action and returns evidence | tool declaration, model decision, framework execution, result feedback | Locate where a tool call is stalled and tell whether a final answer is grounded | Treats model-generated tool-call text as if the external tool already ran | Stable |
| distinguish three Agent learning mechanisms | Need to decide where an Agent should acquire or preserve a capability | post-training, in-context learning, externalized learning, persistence, update cost | Classify an adaptation by what changes and predict whether it persists | Calls every use of examples or knowledge bases model training | Stable |
| separate context into static prefix and dynamic trajectory | Need to explain what an LLM sees on each Agent iteration | system prompt, tool definitions, user messages, assistant messages, tool results | Classify context components and trace what accumulates across iterations | Calls all context a prompt or treats tool results as external to context | Stable |
| run a ReAct feedback loop | Need to explain or debug how an Agent advances across multiple tool calls | reasoning, acting, observing, trajectory accumulation, exit conditions | Trace one iteration and use observations to choose the next action | Repeats actions without incorporating tool results or omits a stop condition | Stable |
| map reliability needs to the five Harness functions | Need to turn a working Agent demo into a production system | context, tools, constrain, verify, correct, prevention vs detection vs recovery | Place each engineering mechanism in the right reliability layer | Treats policy text as a hard constraint or model claims as external verification | Stable |
| classify Prompt, Context, Harness, and Loop Engineering by scope | Need to identify which engineering discipline owns a system concern | instructions, visible information, runtime infrastructure, cross-run autonomy | Place an intervention at the narrowest correct engineering layer | Treats newer layers as replacements instead of expanding supersets | Stable |
| distinguish inner ReAct execution from cross-run Loop Engineering | Need to keep a long-running Agent progressing after one task or context window ends | per-run ReAct, Harness reliability, persistent state, next-task discovery, global completion | Tell who advances the next run and prevent local success from being mistaken for global completion | Treats one successful ReAct run or passing test as completion of the whole long-term goal | Stable |
| diagnose Agent design with simplicity, transparency, and ACI | Need to improve an Agent that is hard to debug or frequently misuses tools | minimal complexity, visible plans and traces, Agent-facing interface design, poka-yoke | Identify whether a failure comes from excess abstraction, poor observability, or a confusing tool interface | Adds framework layers first, hides execution traces, or exposes vague tool names and parameters | Stable |
| choose an Agent model by task fit | Need to select a model for a concrete Agent workload | reasoning and tool use, task evaluation, output speed, multimodality, cost, deployment, compliance | Reject a high-ranked model when it violates workload constraints and design a task-specific evaluation | Chooses by a generic leaderboard or vendor reputation alone | Stable |
| use control ownership to separate Workflow and Agent | Need to decide whether an LLM system is a workflow or an agent | code-controlled flow, LLM-controlled flow, reliability vs flexibility | Classify automation designs and choose workflow, agent, or hybrid | Calls any LLM automation an Agent | Stable |
| place guardrails by input, execution, and output risk | Need to secure an Agent action from request intake through external effects and final response | input classifiers and rules, tool risk rating, output validation, PII filtering, human escalation | Put each defense at the correct boundary and identify high-risk actions needing approval | Relies on one filter for all threats or asks for approval only after an irreversible action | Stable |
| design a reliable Agent end to end | Need to transfer chapter concepts into a production design | components, ReAct, Harness, orchestration, guardrails, human escalation, Loop completion | Produce a coherent system design from perception through verified action and global completion | Lists concepts separately without assigning control ownership, verification, recovery, or completion gates | Forming |
| map Function Call, MCP, Skills, and A2A by layer | Need to compare Agent ecosystem terms in interviews | atomic tool call, tool standardization, behavior instruction, agent collaboration | Explain which layer each technology solves and avoid category confusion | Mixes protocol/tool/methodology boundaries | Not started |
| audit Agent readiness by code, process, and environment context | An Agent looks capable but produces project-incompatible or non-deployable work | code structure and conventions, workflow and CI rules, runtime and deployment environment | Locate the missing information class before blaming the model and predict a concrete failure | Recommends a larger model without identifying which project context is absent | Forming |
| reconstruct a stateless Agent API call from message roles | Need to build or debug the request after a model asks to use a tool | system, user, assistant tool_calls, tool result, tool_call_id, full-history replay | State which messages must be preserved and connect each real tool result to the model decision that requested it | Sends only the tool result, labels it as user, drops the assistant tool-call message, or omits the tool_call_id link | Forming |
| preserve prefix stability for KV and Prompt Cache reuse | Need to place dynamic state or diagnose rising TTFT and inference cost | byte-stable prefix, cached K/V projections, append-only dynamic information, cache invalidation | Predict which context edits force recomputation and relocate dynamic data without rewriting the prefix | Inserts timestamps or changing user state into system prompt, dynamically reorders tool definitions, or omits the latency and cost consequence of recomputation | Forming |
| distinguish KV Cache from Prompt Cache by scope | Need to explain which cache is reducing work within generation versus across API requests | model-internal token K/V reuse, API service prefix matching, cross-request KV reuse, shared prefix-stability requirement | Classify a cache hit by execution layer and predict whether it affects decoding work or repeated request prefill | Calls every prefix reuse KV Cache or treats Prompt Cache as a separate representation unrelated to K/V | Forming |
| locate KV and Prompt Cache across runtime and hardware layers | Need to explain where cached K/V tensors physically live in self-hosted versus API inference | inference runtime, GPU VRAM or HBM, CPU DRAM, optional offload, provider-managed cross-request cache | Identify who owns the cache and which memory hierarchy usually holds active versus offloaded state | Treats KV Cache as CPU L1/L2/L3, assumes Prompt Cache lives on the API caller's machine, or claims one universal physical location | Forming |
| turn unordered rule piles into executable SOPs | An Agent knows many instructions but skips stages, mishandles exceptions, or forgets verification | ordered stages, current execution state, branch conditions, stop conditions, final verification | Rewrite scattered behavioral rules as a process the model can execute and diagnose | Keeps appending isolated MUST rules without specifying order, branches, or completion checks | Forming |
| turn product intent into executable decision boundaries | A business policy sounds reasonable but equivalent cases receive inconsistent outcomes | inclusion criteria, explicit exclusions, thresholds, units, rounding, product ownership | Convert a vague policy into deterministic classification and calculation rules | Lets the model invent what counts as savings, success, or an exception based on plausible language | Forming |
| distinguish three service pricing modes by what the customer pays for | Need to classify a billing-Agent task before applying business-rule boundaries | percentage of negotiated savings, fixed service fee, difficult-task upfront non-refundable payment | Identify each pricing mode from the object and timing of payment | Treats every reduction in future spending as negotiated savings or interprets fixed-fee tip as optional gratuity | Forming |
| choose rules or Few-shot examples by pattern describability | Need to teach an Agent a desired behavior, style, or output form inside context | explicit rules, demonstrated patterns, 2–3 boundary examples, token cost, prefix stability | Choose concise rules for definable behavior and examples for patterns that are easier to show than describe | Adds many examples for a simple rule or keeps adding vague adjectives when concrete examples would communicate the pattern | Forming |
| write tool definitions as agent-facing operating manuals | An Agent has valid function schemas but chooses the wrong tool or supplies invalid values | purpose, usage boundaries, parameter examples, performance hints, inter-tool relations | Diagnose and enrich a bare tool signature so the model can select and call it correctly | Assumes a function name and JSON types are enough for the model to infer safe use and valid parameter semantics | Forming |
| treat external content as untrusted data rather than executable instruction | An Agent reads webpages, emails, documents, metadata, retrieved knowledge, or third-party capabilities | prompt injection, source trust, role hierarchy, external-content marking, layered execution defenses | Classify instruction-looking text by its source and prevent untrusted data from gaining command authority | Executes commands embedded in retrieved content or relies on one warning string as complete protection | Forming |
| layer prompt-injection defenses across context and execution | An Agent consumes untrusted content and can perform consequential external actions | source labels, role separation, input cleaning, permissions, sandboxing, independent review, high-risk confirmation | Explain what each defense layer can and cannot guarantee and place enforcement before irreversible effects | Treats XML tags or a system warning as sufficient protection for sensitive tool calls | Forming |
| use Skills to progressively disclose domain capabilities | Many domain capabilities are available but a task needs only a small subset | metadata directory, routing description, on-demand SKILL.md, selective references, scripts, templates | Keep discovery cheap while loading only the workflow and details required by the current task | Injects every complete Skill into the permanent prompt or writes broad descriptions that trigger irrelevant Skills | Forming |
| append Skill instructions without rewriting the cached prefix | A running Agent discovers that it needs a new domain workflow after a long trajectory has accumulated | system-prefix rewrite, middle-context file read, dedicated Skill tool result, append-only cache growth, instruction-following strength | Choose a placement that preserves prior cache while giving loaded instructions sufficient execution salience | Rewrites the system prompt whenever a Skill changes or assumes cache-friendly loading has zero first-write cost | Forming |
| distill implicit trajectory state into status readings plus policy | An Agent loses count, forgets TODOs, repeats actions, or sees telemetry without changing behavior | Harness-computed state, structured status fields, end-of-context attention, readout-to-action policy | Replace repeated scanning of raw trajectory with reliable explicit state that directly guides the next decision | Asks the model to recount long logs every turn or provides timestamps and counters without saying how they should affect action | Forming |
| choose replace or append status updates by cache and staleness cost | A dynamic status block changes repeatedly during an Agent trajectory | replace-old-state invalidation, persistent append, stale-version accumulation, trajectory length, update size and frequency | Select an update mode by comparing cache recomputation cost with token and ambiguity cost | Always replaces for cleanliness or always appends for cache without considering trajectory length and state size | Forming |
| distinguish context overflow from context rot | An Agent degrades as its trajectory grows, even when the context window may not be full | capacity exhaustion, information density, attention dilution, position bias, retrieval failure | Diagnose whether the system cannot fit more tokens or can still fit them but can no longer reliably find and use key information | Waits for the window to reach its hard limit before compressing noisy context | Forming |
| trade one controlled cache rebuild for task-aware batch compression | Tool results and long trajectories are reducing useful context density, but rewriting history invalidates cache from the replacement point | stable prefix, tool-result replacement, suffix cache invalidation, rot or capacity trigger, batch compression | Decide when the gain in task-relevant information density justifies one deliberate cache rebuild | Compresses every round to keep context tidy, or refuses all compression merely to preserve cache | Forming |

## Status Values

- Not started: named but not taught yet.
- Forming: introduced and practiced, but not stable.
- Stable: learner can explain and apply it in near-transfer tasks.
- Needs review: learner missed it, confused its boundary, or failed to transfer it.
